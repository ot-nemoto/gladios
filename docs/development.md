## ディレクトリ構成

```
/                     Vite + TypeScript のブラウザゲーム本体（package.json はルート）
├─ src/
│  ├─ sim/            戦闘判定の中核。DOM・乱数・時計を使わない純粋な TS（決定性を守る層）
│  │  └─ trig.ts      三角関数の唯一の入口。sim/ では Math.sin 等を直接呼ばない
│  ├─ data/           docs/prototype から写したデータ（手で直さない）
│  ├─ scenarios/      確認用シナリオ（ビューアと Python 一致テストで共用）
│  ├─ render/         描画（Canvas 2D。今は判定領域をそのまま描く骨格表示、後でドット絵に差し替え）
│  └─ ui/             画面（戦闘ビューアと判断パネル・剣闘士の設定、モーション図鑑。作戦編集は今後）
├─ tests/             Vitest
├─ scripts/           補助スクリプト（sync-data.mjs、dump_golden.py など）
└─ docs/
   ├─ development.md  この文書（開発者向け）
   ├─ 01_ゲーム企画・基本設計書.md
   ├─ グラフィックス方針メモ.md
   └─ prototype/      Python 試作・キーフレーム・確認条件・check-*.txt
```

- 設計書 §14 などに出てくるファイル名（`sim_prototype.py`、`check-*.txt`、`keyframes-full.json` など）は、すべて `docs/prototype/` にある。設計書本文はライブラリの原本と揃えるため、パスの書き換えはしていない。
- キーフレームと確認条件の正は `docs/prototype/` 側。更新したら `npm run sync:data` で `src/data/` へ写す（ずれはテストで検知される）。

### コマンド

| コマンド | 内容 |
|---|---|
| `npm run dev` | 開発サーバー（http://localhost:5173/ 。`/` が戦闘ビューア、`/motions.html` がモーション図鑑） |
| `npm run build` | 型検査＋本番ビルド |
| `npm run preview` | 本番ビルドを手元で確認 |
| `npm run typecheck` | 型検査だけ |
| `npm test` | テスト（`npm run test:watch` で変更を監視して繰り返す） |
| `npm run sync:data` | `docs/prototype/` のデータを `src/data/` へ写す |
| `npm run golden` | Python 試作の出力を `tests/golden/sim-prototype.json` に書き出す（TS 移植の正解データ） |

### 実装の約束

- 変更したら `npm run typecheck` と `npm test` を通す。
- `src/sim/` は決定性を守る。`Math.random`・`Date`・DOM を使わない。三角関数は `trig.ts` 経由（現在は Python 試作と一致させるため標準の Math。環境間の完全一致が要る段階で自前実装に差し替える）。
- 戦闘の正式な記録はイベントログ（設計書 §5.9）。
- `src/sim/` の判定本体（`sim.ts` と、それが使う `body` / `contact` / `rules` / `select` など）は Python 試作 `sim_prototype.py` の忠実な移植で、`src/scenarios/check-scenarios.json` の全シナリオでログ・結果・最終状態が Python と完全一致することをテストで確認している。`src/sim/` の判定本体の振る舞いを変えるときは（規則の変更でも、試作にもある不具合の修正でも）、先に Python 試作を直し、`npm run sync:data`（キーフレーム・確認条件を写す）→ `npm run golden`（正解データを作り直す）の後に TS 側を合わせる。TS の移植だけの誤り（試作は正しい）を直す場合は、試作も正解データも変えずに TS を直す。
- 判定は判断のたびに、判断の過程（調べたルールとルールが見た値、部位の点数の内訳、間合い、相手への反応の予定）を `src/sim/trace.ts` の形で `Sim.trace` に書き足す（戦闘ビューアの判断パネル用）。表示のための記録で、判定の結果・ログには影響させない（Python 試作には無く、一致テストの対象外）。記録には値だけを持たせ、説明の文言は `src/ui/` で作る。しきい値は判定と同じ定数（`data.ts`）を使う。
- `src/sim/record.ts`（リプレイの記録）と `src/sim/motion.ts`（モーション図鑑の計算）は移植ではなく、判定と同じ関数・定数を使う補助。判定と食い違わないよう、接触の分類（`contact.ts`）や行動時間の定数（`data.ts`）は判定と共有し、独自に書き写さない。画面だけで使う名前は `src/ui/` に置く。判定のログの文言が使う名前（部位・強さ・攻撃方法の日本語名など。Python 試作から移植した文言）は `src/sim/data.ts` に置き、画面からも共有する。

## 設計の進め方の約束（重要・必ず守る）

- **1回に1つの論点**だけを扱う。まず推奨案を理由と懸念つきで提示し、ユーザーの承認を得てから決定として仕様書に反映する。承認されていない提案を決定にしない。
- ユーザーの「OK」は、直前の提案への承認を意味する。ユーザーが考えながら覆すこともあるので、その場合は議論を続ける。
- 戦闘は**完全決定性**（乱数による命中・成功率を持たない。同じ入力は同じ結果）。差は速度・タイミング・位置・軌道・行動の質でつける。
- ファンタジー要素は入れない。舞台は紀元80年頃のローマ。
- 数値は原則「仮置き」。決定と仮置きと未決定を区別して書く。
- 仕様が変わったら、本文の該当節と §12 の変更履歴の両方を更新する。試作で規則を検証したら `check-*.txt` に記録を残し、§14 にも1行残す。
- このリポジトリの設計書は作業用ドラフト。ユーザーの手元（ライブラリ）にある原本とは版管理が別で、そちらへの反映はユーザーが行う。

## 作業の流れ（Issue・ブランチ・PR）（必ず守る）

- **作業単位ごとに GitHub Issue を作る。** ブランチを切る前に、目的・作業内容・完了条件を書いた Issue を `gh issue create` で立てる（設計の論点も1論点＝1 Issue）。以下、Issue → ブランチ → コミット → PR → レビュー → マージ の順に進める。
- **Issue 作成時、または実装完了後に、動作確認一覧を Issue 本文へ追加する。** 確認する操作・条件と期待する結果をチェックリストで記載し、実施後は結果を Issue に残す。確認済みの項目には ✅ を付け、チェックリストもチェック済みにする。未確認・検証できない項目には ✅ を付けず、未チェックのまま理由を記載する。AI 側で動作確認できる項目は AI が実施し、ブラウザでの確認が必要なら Playwright を利用してよい。どうしても検証できない項目がある場合は、未検証であることと理由・確認手順・期待する結果を明記し、その項目の確認をユーザーへ依頼する。
- **ブランチ**は `develop` から切る。名前は `<種類>/<Issue番号>-<短い説明>`（例: `feature/12-strategy-rules`、`fix/15-approach-overshoot`）。複数 Issue をまとめて扱う場合は代表の内容で名付ける。種類は `feature` / `fix` / `docs` / `chore` / `refactor`。
- **コミットメッセージ**には対応する Issue 番号を `(#12)` の形で入れる。
- **PR** は `develop` 向けに出し、本文に `Closes #12` の形で対応する Issue をすべて書いて紐づける（マージで自動クローズされる）。
- **PR を作成したら、その PR に対してエージェントによるコードレビューを行う**（Claude Code の `/code-review high <PR番号>`）。
  - 対象外：develop → master の自動 PR（`auto-pr-to-master.yml`。中身は各 PR でレビュー済み）と、Dependabot の npm の更新 PR（CI で確認する）。
  - Dependabot の devcontainers・GitHub Actions の更新 PR は、マージする前にレビューする（CI は開発コンテナの構築や、Pages 配信・リリースのワークフローを実行しないため）。直す必要がある指摘が出たら、Dependabot のブランチには push せず、Issue にして PR を保留するか閉じる。
  - 指摘ごとに次のどれかで対応する。
    - **直す**：その PR の変更で入った問題（Python 試作・正解データの変更も含む）。直し方に仕様の判断が要る場合は、ユーザーに確認してから直す。
    - **Issue にする**：PR が変えていない既存の問題、PR の範囲外の改善。
    - **不採用**：指摘が誤っている、または対応しない方がよいもの。理由を書く。
  - 「直す」で変更を push したら、**再レビューを 1 回だけ**行う。レビューは PR 全体を見直すので、前回と同じ指摘や、既に判断した指摘は扱わない。「直す」の対象にするのは、その修正で入った問題だけ（それ以外の新しい指摘は「Issue にする」か「不採用」）。再レビューの指摘をさらに直した場合は、もう一度はレビューせず、結果のコメントに書いてユーザーの確認を受ける。
  - 結果（指摘と、それぞれの対応と理由）を PR にまとめのコメントで残す。対応の記録になるため、`--comment` による行コメントの投稿では代えない。
  - レビュー対象の PR は、レビュー（必要なら再レビュー）・結果のコメント・CI が済んでからマージする。
- **PR のマージはマージコミット**で行う（squash しない）。master への自動 PR が「Merge pull request #N」から PR と Issue を拾うため。
- 作業中に見つかった別件は、その場で直さず新しい Issue にする。

## CI・公開・リリース（GitHub Actions）

| ワークフロー | いつ | 何をする |
|---|---|---|
| `ci.yml` | PR、develop への push | 型検査・テスト・ビルド |
| `secret-scan.yml` | PR、毎週月曜 | gitleaks で秘密情報の混入を検出（PR は差分、定期は全履歴） |
| `deploy-github-pages.yml` | develop への push | 戦闘ビューアとモーション図鑑を GitHub Pages に公開（https://ot-nemoto.github.io/gladios/ 、図鑑は `motions.html`） |
| `auto-pr-to-master.yml` | 毎朝 6:00（JST） | develop → master の PR を作成・更新。含まれる Issue に `enhancement` があれば `bump:minor`、なければ `bump:patch` を付ける |
| `bump-version.yml` | master 向け PR に bump ラベル | package.json の版を上げてコミット |
| `release.yml` | master への push | package.json の版でタグと GitHub Release を作る |
| `dependabot.yml` | 毎週 | npm・devcontainers・GitHub Actions の更新 PR を develop 向けに作る |

- 自動 PR にはリポジトリのシークレット `AUTO_PR_TOKEN`（PR とラベルを操作できるトークン）が必要。
- gitleaks の版は Dependabot の対象外なので、`secret-scan.yml` の版とチェックサムを手で更新する。
